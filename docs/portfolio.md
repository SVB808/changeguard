# ChangeGuard portfolio and interview guide

This document is the concise engineering narrative behind ChangeGuard V1. It is written to help reviewers understand the problem, the architecture, the evidence boundaries, and the tradeoffs without reading the full implementation history.

## One-line project summary

ChangeGuard is a deterministic-first change-impact and release-risk engine for Java/Spring microservices that traces provider-side API changes to downstream consumers, plans revision-bound verification, and uses constrained AI only for grounded evidence selection.

## Problem statement

A pull request can change one service while breaking another service that is not modified in the diff. Traditional diff review is weak at answering questions such as:

- Which downstream services depend on the changed contract?
- Does a consumer still call an old endpoint path or method?
- Which verification command should be run for the affected Maven module?
- Was verification run against the exact Git revision that was analyzed?
- Can an LLM summarize the result without inventing unsupported evidence?

ChangeGuard treats these as separate evidence, inference, verification, and synthesis problems rather than delegating the entire workflow to a model.

## Architecture narrative

The V1 pipeline is:

```text
GitHub PR / Git refs
  -> change extraction
  -> Java/Spring AST semantics
  -> module-scoped service graph
  -> explicit consumer call-site evidence
  -> cross-service impact refinement
  -> revision-bound verification plans
  -> optional explicit local verification
  -> typed verification evidence
  -> constrained evidence-ID selection
  -> deterministic grounding + policy closure
  -> deterministic report
```

The core design rule is:

```text
evidence -> inference -> verification -> grounded synthesis
```

The deterministic system owns facts and safety invariants. A model may help rank or select supplied evidence, but it does not become the source of truth.

## Engineering decisions worth discussing in interviews

### 1. Deterministic-first instead of model-first

Source semantics, dependency evidence, impact candidates, verification plans, and grounding validation are deterministic. This makes failures inspectable and lets model quality be evaluated separately from core correctness.

Tradeoff: deterministic analyzers require more implementation work and support a narrower set of frameworks than a generic LLM prompt. The benefit is a much stronger correctness boundary.

### 2. Module-scoped service identity

Service identity is scoped to repository modules rather than inferred from simple names alone. This avoids collisions in multi-module repositories and keeps consumer/provider relationships tied to concrete source locations.

### 3. Exact consumer-call refinement

Service-level dependency evidence is useful but often too broad. ChangeGuard refines impact when it can prove a concrete consumer method + route through WebClient, OpenFeign, or RestTemplate evidence.

Tradeoff: static/literal routes are supported more strongly than highly dynamic URL construction.

### 4. Reactor-aware Maven verification

Verification commands are generated from repository/module layout and can use a parent reactor with `-f`, `-pl`, and `-am` rather than assuming the affected module can always be tested independently.

### 5. Revision binding before execution

Generated plans record the analyzed Git head. Before Maven runs, `verify-plan` checks `git rev-parse HEAD`. A mismatch returns an error and refuses execution.

This prevents a subtle evidence-integrity bug: analyzing commit A and accidentally attaching test results from commit B.

### 6. AI as an evidence selector, not an autonomous reviewer

The model receives typed evidence and can return only evidence IDs. Unknown IDs, duplicates, and over-budget selections are rejected. Deterministic policy closure restores runtime-mandatory evidence before rendering.

This means a model can help prioritize context without gaining authority to invent facts or execute repository code.

### 7. Raw model quality vs effective policy quality

ChangeGuard evaluates raw selector output and post-policy effective output separately. This avoids hiding model errors behind deterministic corrections and makes the system's actual safety boundary measurable.

## Evaluation discipline

The V1 deterministic impact corpus contains 24 controlled cases. CI requires exact disposition + verification-plan expectations across the corpus and reports impact/endpoint TP, FP, TN, FN, precision, recall, FPR, technology breakdown, and deterministic-core latency.

The runtime-shaped release evaluation uses evidence generated by production `collect_evidence()` paths and verifies grounding plus runtime policy-mandatory retention. These are controlled-corpus and runtime-shaped fixture metrics, not production-accuracy claims.

Model evaluation is intentionally separated because local/cloud model outputs can vary by provider, model version, runtime, cache state, and sampling implementation even when nominal temperature/seed settings are fixed.

## Safety invariants

- Remote PR analysis never automatically executes target project code.
- Verification execution is an explicit local action.
- Generated verification is bound to the analyzed Git revision.
- Unknown model evidence IDs fail validation.
- The effective report cannot silently drop runtime-mandatory evidence.
- Mandatory evidence over the budget fails closed.
- A passing verification command is not described as universal proof of safety.
- A failing command is not described as automatic proof that the analyzed change caused the failure.
- Controlled benchmark results are never labeled as production accuracy.

## Strong demo sequence

Use `docs/demo.md` for commands. In an interview or portfolio walkthrough, the useful story is:

1. Show a provider endpoint path change.
2. Show how ChangeGuard identifies explicit downstream consumer call sites.
3. Show the endpoint-level impact candidates and Maven verification plans.
4. Point to `expected_head` and explain the revision-binding refusal path.
5. Run synthesis with the deterministic selector or Ollama.
6. Explain that the model returns evidence IDs only and that deterministic policy closure remains authoritative.
7. Run the release evaluation and explain what its metrics do and do not claim.

Use only bullets that fit the target role and available resume space.

**Backend / platform emphasis**

- Built ChangeGuard, a Python + Java static-analysis engine that traces Spring REST contract changes across module-scoped microservice dependencies and WebClient/OpenFeign/RestTemplate call sites to identify downstream release impact.
- Designed reactor-aware, revision-bound Maven verification planning that targets affected consumer modules and refuses execution when the local Git revision differs from the analyzed PR head.
- Implemented deterministic evaluation and release gates over controlled impact and runtime-shaped evidence corpora, separating core change-impact correctness from provider/model behavior.

**AI / agentic software emphasis**

- Built a grounded LangGraph synthesis pipeline where LLMs can select only precomputed evidence IDs; deterministic guardrails reject fabricated/duplicate evidence and restore decision-critical runtime evidence before rendering.
- Evaluated local Ollama and optional OpenAI evidence selectors independently from the deterministic core, including grounding, evidence recall/precision, distractor rate, consumer coverage, verification retention, and reproducibility behavior.
- Designed explicit tool boundaries so AI reasoning cannot parse arbitrary new source, execute project commands, or overwrite deterministic release evidence, providing a practical constrained-agent architecture for software engineering workflows.

## 60-second interview answer

"ChangeGuard answers a problem that normal code review misses: a PR can modify one service and break another service outside the diff. I built a deterministic pipeline that parses Spring endpoint changes, builds a module-scoped dependency graph, identifies explicit WebClient, Feign, and RestTemplate consumers, and generates targeted Maven verification plans. Those plans are bound to the exact analyzed Git SHA, so execution is refused if the local checkout does not match. I then added LangGraph-based synthesis, but the model never becomes the source of truth: it can only select existing evidence IDs, and deterministic grounding and policy closure remain authoritative. I also built separate evaluation paths for deterministic impact correctness and model-selection quality so I don't hide model mistakes behind guardrails or claim controlled benchmarks are production accuracy."

## Deeper interview questions to prepare for

**Why not just send the diff to an LLM?**

Because the important information can live outside the changed files, and unconstrained model output makes evidence provenance difficult to verify. ChangeGuard first constructs deterministic cross-service evidence, then lets a model operate inside that boundary.

**Why use JavaParser instead of regex?**

Spring endpoint meaning depends on syntax structure, annotations, class-level + method-level composition, and before/after source context. AST extraction gives a more explicit semantic model and is easier to test than increasingly complex regex rules.

**Why keep deterministic policy closure after model selection?**

Model selection can omit critical evidence even when it is grounded. The policy layer guarantees that runtime-mandatory evidence survives in the effective report while still exposing the raw model result for evaluation.

**What would you build next?**

The strongest extensions are Gradle verification planning, database migration compatibility, messaging schema/consumer compatibility, broader dynamic HTTP-client extraction, sandboxed verification, and GitHub Check/PR comment integration. These should be added without weakening the deterministic evidence and execution boundaries.

## Claim discipline

For interviews, resumes, and public documentation, prefer phrases such as "controlled corpus," "runtime-shaped fixtures," "deterministic release gate," and "effective policy retention." Avoid describing the benchmark numbers as production accuracy, arbitrary-repository coverage, or proof that every detected impact will fail at runtime.
